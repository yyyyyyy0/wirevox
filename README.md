# WIREVOX

[English](README.en.md)

WIREVOX は、マイクの音に VST3 プラグイン（ボイスチェンジャー、EQ、ノイズ除去など）を順に掛けて、仮想オーディオデバイスへ出力する macOS 用のアプリです。通話や配信のマイクに好きなエフェクトを掛けたいけれど、普通の DAW では遅延が大きい、という人向けです。通話アプリ側では、その仮想デバイスをマイクとして選びます。

マイク → VST3 プラグイン → 仮想デバイス（BlackHole、Loopback など）→ 通話・配信アプリ

## できること

- 遅延が小さい。マイクの取り込みから出力までを 1 回の処理でまとめて行い、バッファを小さくして遅延を抑えます。
- 遅延の内訳が画面に出る。入力機器、バッファ、各プラグイン、出力デバイス、仮想デバイスが足す分のどこが大きいかが分かります。プラグインごとの処理時間も出ます。
- MIN LATENCY で自動調整できる。音切れしない最小の遅延を探します。ゲームや配信向けの「余裕あり」と、静かなときの「最速」があります。
- モニター出力がある。処理した声を、通話の相手に送る出力とは別のデバイスで、自分だけ聞けます。
- かんたん表示と詳細表示を切り替えられる。
- 見た目を 4 つのテーマから選べる。
- 設定は自動で保存され、次回起動時に戻ります。

## 必要なもの

- macOS（動作確認は Apple Silicon の Mac だけです）
- Command Line Tools または Xcode
- CMake 3.22 以上
- 仮想オーディオデバイス（BlackHole、Loopback など。出力先として使います）
- 使いたい VST3 プラグイン

## ビルド

JUCE（オーディオアプリ用の C++ ライブラリ）は git submodule（`JUCE/`、タグ 9.0.5）です。ビルド中にネットワークは使いません。

```sh
git clone --recursive https://github.com/yyyyyyy0/wirevox.git
cd wirevox
# すでに clone 済みで JUCE/ が空のときは次を実行します
git submodule update --init
cmake -S . -B build -G "Unix Makefiles" -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
```

成果物: `build/Wirevox_artefacts/Release/WIREVOX.app`

```sh
open build/Wirevox_artefacts/Release/WIREVOX.app
```

Command Line Tools の入れ方によっては、clang が標準 C++ ヘッダ（`<algorithm>` など）を見つけられないことがあります。`CMakeLists.txt` が検出して、SDK 内の libc++ ヘッダを使うように自動で切り替えます。

## 使い方

1. 初回起動ではデバイスを開きません。マイクがスピーカーに直結してハウリングするのを避けるためです。左のパネルで、出力（仮想デバイス）と入力（マイク）を選びます。
2. 入力チャンネルは、マイクがつながっているチャンネルだけにチェックを入れます。1 チャンネルなら左右の両方に同じ音を送ります。2 チャンネル以上なら、1 番目を左（L）、2 番目を右（R）にします。
3. 「プラグインを追加...」から `.vst3` を選ぶか、`.vst3` をウィンドウへドロップします。追加はこのファイルだけをスキャンします。
4. 「上」「下」ボタンで順番を変え、「バイパス」でプラグインを一時的に外し、「編集」でプラグイン自身の画面を開きます。
5. 右下に、サンプルレート、バッファ、入出力デバイスの遅延、プラグイン遅延、合計（ms）、処理の負荷（平均と最大）、オーバーロード数（処理が間に合わなかった回数）、遅れたコールバック数（音声処理の呼び出しが遅れた回数）が出ます。遅延を小さくするには、バッファサイズを小さくします。
6. 「MIN LATENCY」を押して「余裕あり」か「最速」を選ぶと、音切れが出ない最小の遅延を自動で探します。ゲームや配信をしながら使うなら「余裕あり」です。
7. 処理した声を別のデバイスでも聞きたいときは、左のパネルの下の「モニター出力」にチェックを入れて、機器とチャンネルの組を選びます。
8. チェーン（プラグインの並び）の下の「LATENCY BREAKDOWN」で、遅延のどこが大きいかと、プラグインごとの処理時間を確認します。「仮想デバイスを計測」を押すと、Loopback などが足している遅延も測れます。

## 主な機能

### MIN LATENCY

チェーンのパネルにあるボタンです。押すとメニューが出て、探し方を選びます。選んだ方式は次回以降も使われます。

- 「余裕あり（ゲーム・配信向け）」: 背景に負荷を掛けながら探します。ゲームや配信で CPU が忙しくても音切れしにくい設定になります。既定はこちらです。
- 「最速（静かなとき向け）」: 負荷なしで探します。何も動かしていない静かなときに、より小さい遅延を狙えます。

探している間は数回デバイスを開き直すので、音が途切れます。全部で 1 分ほどかかります。サンプルレートは変わりません。結果は画面下のステータス行に出ます。ゲームを動かしたまま押すと、実際に近い結果になります。

### 遅延の内訳と計測

メイン画面のチェーンの下（LATENCY BREAKDOWN）に、遅延を部分ごとに分けて常時表示します。いちばん大きい行には「ここが最大」の印が付きます。各行には、デバイスが自分で報告した値（申告値）か、実際に測った値（実測）かを示すタグが付きます。

- 「仮想デバイスを計測」を押すと、確認ダイアログが出ます。数秒のあいだ、出力デバイスに試験音が流れ、マイクの音は止まります。通話中なら、相手に試験音が聞こえます。「計測する」を選んだときだけ始まります。
- 計測の結果は、出力デバイスとサンプルレートの組で保存され、次回起動時も同じ条件なら表示されます。
- 内訳の下には、プラグインごとの処理時間が出ます。1 バッファの時間に対する割合で、直近 3 秒の平均と最大です。最大がいちばん大きいプラグインに「ここが重い」の印が付きます。
- 計測中は、MIN LATENCY、デバイスの選択、プラグインの追加・削除・並べ替え・バイパスは使えません。

### モニター出力

処理した声を、通話の相手に送る出力とは別のデバイス（例: オーディオインターフェースの出力 3/4）でも鳴らします。通話の相手に届く音は変わりません。

1. 左のパネルの下の「モニター出力」にチェックを入れます。
2. 「モニター機器」で出力先のデバイスを選びます。
3. 「ch」で左右の組を選びます。1/2、3/4 のように、奇数番号から始まる組です。

チェックを入れるまでは、何も作らず、デバイスも開きません。Audio MIDI Setup の設定には触りません。

### かんたん表示と詳細表示

ロゴの右、テーマ選択の左にあるボタンで、画面全体を切り替えます（音には影響しません）。選んだ表示は次回起動時に戻ります。

- かんたん表示: 合計の遅延を大きな数字で出し、いちばん大きい部分を 1 行、状態（「安定」か「音切れ N 回」）を 1 行で出します。気をつけることがあるときだけ「注意:」の行が出ます（サンプルレートの食い違い、モニターの待機や失敗、いちばん重いプラグインがバッファ時間の 70 % 以上、のとき）。遅延の内訳のパネルは畳まれ、「仮想デバイスを計測」のボタンだけが残ります。
- 詳細表示: 内訳やプラグインごとの処理時間を含む、すべての情報が出ます。

設定ファイルがまだ無い初回起動は、かんたん表示で始まります。ボタンの文字は、かんたん表示のときは「詳細を表示」、詳細表示のときは「かんたん表示」です。

### テーマ

右上のセレクタで見た目を切り替えます（すぐ全体に反映されます）。選んだテーマは次回起動時に戻ります。

| id | 名前 | 見た目 |
| --- | --- | --- |
| `rack84` | RACK '84 | 炭色のブラシ仕上げ金属、ラックのねじ、丸い LED、緑の LCD |
| `terminal` | TERMINAL | 緑リンの CRT、等幅、文字のボタン `[ 編集 ]`、状態は `ON` / `BYP` / `ERR` |
| `desktop95` | DESKTOP '95 | グレーの 90 年代デスクトップ、紺のタイトルバー、チェックボックス |
| `neon` | NEON | シンセウェーブ、地平線のグリッド、光る輪郭、ピル型ボタン |

## 困ったとき

- 音がパリパリ切れる: バッファサイズを上げます。「MIN LATENCY」で「余裕あり」を選んで探し直す方法もあります。サンプルレートを下げると負荷が減ることもあります。
- サンプルレートの警告が出る: 入力機器か出力デバイスが、アプリの動作レートとは別のレートで動いています。この場合、間でレート変換が入り、遅延と負荷が増えます。機器側のレートをアプリに合わせると解消することがあります（詳しくは技術メモの「サンプルレートの扱い」）。
- モニターが「待機中」になる: モニター機器かメイン出力のデバイスが、今は見つかっていません。接続や電源を確かめてください。デバイスが現れると、自動で 1 回だけ試し直します。
- 入力が無音になる: マイクへのアクセスは、初回起動時に macOS が確認します。許可していないと入力は無音になります。システム設定でこのアプリのマイクを許可してください。

## 技術メモ

ここから下は、仕組みや設定の詳細です。使うだけなら読む必要はありません。各項目は、クリックで開きます。

<details>
<summary>サンプルレートの扱い</summary>

- 遅延を小さくするには、バッファサイズを小さくします。
- JUCE はデバイスを開くとき、設定ファイルのサンプルレート（`audioDeviceRate`）を `kAudioDevicePropertyNominalSampleRate` としてデバイスに書き込みます。そのため、アプリがレートを変えないとは言えません。
- 仮想デバイスはアプリのレートに追従して書き換わることがあります（Loopback の仮想デバイスで、44100 から 48000 に変わった例があります）。
- 入力機器が設定のレートで動けない場合（例: 入力が 192 kHz、アプリが 44.1 kHz）は、機器のレートはそのままで、JUCE が内部で作る機器セット（aggregate device。複数のデバイスを 1 つにまとめたもの）がレート変換（ドリフト補正）をします。
- この書き込みはアプリからは止められません。そこで、入力機器と出力デバイスの両方について、開いた直後の本来のレートがアプリの動作レートと違うときは、ステータス行に警告を出します（レート変換が入り、遅延と負荷が増えます）。
- `--measure` などは、デバイスを開く前と後の両方のレートを入力・出力ごとに表示し、動いていれば `CHANGED` と知らせます。

</details>

<details>
<summary>遅延の測り方（<code>--measure</code> の仕組み）</summary>

アプリの中で「入力に試験音を入れてから、出力デバイスの入力側で聞こえるまで」を測ります。ケーブルは要りません。

```sh
APP=build/Wirevox_artefacts/Release/WIREVOX.app/Contents/MacOS/WIREVOX
"$APP" --measure --settings <設定ファイル>                 # 10 回測って中央値・最小・最大・相関の質を出す
"$APP" --measure --settings <設定ファイル> --with-chain    # 実際のプラグインを通して測る（遅延の申告値を引く）
"$APP" --measure-sweep --settings <設定ファイル>           # バッファとスイッチを総当たりして、安定する最速を探す
"$APP" --tune --settings <設定ファイル>                    # MIN LATENCY と同じ探索をウィンドウなしで（既定は最速）
"$APP" --tune --headroom --settings <設定ファイル>         # 余裕あり（背景の負荷つき）で探す。--fastest は最速を明示
```

設定ファイルと実行時の扱い:

- 設定ファイルは、実際の設定（`~/Library/Application Support/WIREVOX/settings.xml`）の写しで構いません。
- `--settings` を付けない場合は `--use-default-settings` が要ります。
- どちらの場合も、ほかの WIREVOX のプロセスが動いていると拒否します（写しでも同じデバイスを開き直して、動いている方の音を途切れさせるため）。動いている WIREVOX がそのデバイスを使っていないと分かっているときだけ `--force` を付けます。
- `--tune` の既定は最速のままです。アプリのメニューの既定は余裕ありですが、既存のスクリプトと、この文書の数字はこの探し方で出したものなので変えていません。
- `--headroom` と `--fastest` は同時に指定できません。
- 結果は設定ファイルと同じフォルダの `measure-<日時>.txt` にも書きます。
- 測定の間、出力デバイスには -20 dBFS の短い試験音が流れ、入力はその間だけ試験音に置き換わります（マイクの音は通りません）。
- 入力機器と出力デバイスの本来のレートを前後で読み、変わっていれば知らせます。

測定の中身:

- 試験音: 50 ms の線形スイープ（300 Hz から 0.4 x レート）。帯域内にエネルギーが収まるのでレート変換を通っても相関のピークが細く（約 30 マイクロ秒）、時間帯域幅積で雑音から 30 dB 以上浮きます。
- 起点: 入力バッファの先頭フレームの「ハードウェアから取り込まれた時刻」（HAL の `inInputTime`。HAL は macOS の音声ドライバ層）。JUCE がコールバックに渡す `hostTimeNs` は、入出力が両方あるとき `inOutputTime`（出力がハードウェアに渡される時刻）で、入力時刻ではありません（`JUCE/modules/juce_audio_devices/native/juce_CoreAudio_mac.cpp` の 1609 から 1615 行）。そこで機器セットに時刻だけを書き留める 2 本目の IOProc を付け、同じサイクルの出力時刻で突き合わせて入力時刻を得ます。
- 終点: 出力デバイスの入力側を生の IOProc で録音し、バッファごとの `inInputTime` に、試験音の先頭の位置（相互相関と小数サンプルの補間）を足した時刻。録音側の入力遅延と safety offset（デバイスが安全のために見込む余裕分）も足します。録音バッファの長さは結果に入りません（録音側のバッファを 64、128、512、1024 に変えても結果は同じで、`--capture-buffer` で試せます）。
- 結果の 3 つの値:
  - `latency`: 入力の取り込みから出力デバイスで利用可能になるまで。
  - `declared`: 同じ区間でホスト自身のサイクルの HAL 時刻が約束する値。JUCE が画面に出す入力 + 出力の遅延と一致する。
  - `excess`: 差。出力デバイスが足している分。
- 雑音の見積もり: 時刻の分解能は mach tick の 41.7 ns、時刻は HAL がサンプル位置から作るので、仮想デバイスではばらつきがほぼ 0（実測の標準偏差は 0.01 ms 以下）。実機の入力デバイスを使う場合は HAL の時刻のゆれが入る可能性があります。相関の質（1 に近いほど試験音がそのまま届いている）とサイドローブ比が悪い回は「REJECTED」として集計から外します。
- 測れないもの: 試験音は機器セットの入力側のあとで入れるため、入力機器自身の遅延（オーディオインターフェースの内部など）と、入力側のドリフト補正（レート変換）が内部で足す遅延は含まれません。これらは HAL の申告値（デバイスが自分で報告する遅延の値）のままです。

</details>

<details>
<summary>測定の例</summary>

44.1 kHz、バッファ 64 サンプルで、オーディオインターフェースから Loopback の仮想デバイスへ出した例です。機器や設定が違えば値は変わります。

| 区間 | 値 |
| --- | --- |
| ホスト自身（HAL の申告。64 + 64 + safety 5 + 4 = 137 サンプル） | 3.107 ms |
| 仮想デバイスが足す分 | 17.415 ms（768 サンプルで一定） |
| 合計 | 20.522 ms |

この例では、仮想デバイスの 768 サンプルは、ホストのバッファサイズにも録音側のバッファサイズにも依存せず、デバイス自身は遅延 0 と申告していました。ホスト側で減らせるのは合計の一部だけ、ということがあります。自分の環境でどこが大きいかは、「仮想デバイスを計測」か `--measure` で確かめられます。

表示される入力・出力デバイスの遅延には、バッファ 1 回分が含まれています。Loopback など仮想デバイスの内部の遅延は、デバイスが申告しないため含まれません。

</details>

<details>
<summary>MIN LATENCY の探索の詳細</summary>

押すと小さなメニューが出て、探し方を選びます。選んだ方で始まり、次回以降もその方がメニューのチェックになります（設定ファイルのルートの `tuneMode` 属性、`headroom` か `fastest`。ないときと未知の値は `headroom`）。

| 方式 | 向き | 音切れの判定 | IO サイクル使用率 |
| --- | --- | --- | --- |
| 余裕あり（`headroom`、既定） | ゲーム・配信・通話 | 背景に負荷を掛けながら見て、負荷の最大がバッファ時間の 50 % 以下 | 触らない（既定の 1.0 のまま。前に下げてあれば既定に戻す） |
| 最速（`fastest`） | 何も動かしていない静かなとき | 負荷なしで、負荷の最大が 85 % 以下（下に書いた従来の探し方そのまま） | 0.75、0.5、0.35、0.25 と下げて探す |

静かなマシンで見つけた最小のバッファは、ゲームやプラグインの画面が CPU を使い始めると音切れします（192 kHz、バッファ 256、サイクル使用率 0.75 は、コールバックに許される時間が約 1 ms しかない例でした）。余裕ありはそれを避けるための方式です。使用率を下げるとコールバックに許される時間も縮むので、余裕ありは使用率の段階を飛ばし、バッファだけを探します。ゲームを動かしたまま押すと、より実際に近い結果になります（結果の文にもそう書きます）。

#### 最速

- 今のバッファサイズから始めて、3 秒ずつ音切れを見ながらバッファを 1 段ずつ下げます。最初から不安定なら上げます。
- 音切れの判定は、オーバーロード、遅れたコールバック、負荷の最大が 85 % を超えること。モニター中は、機器セットが開けないバッファも「安定しない」として扱います。
- 安定する最小のバッファが見つかったら、12 秒かけて確かめ直します。音切れが出たら 1 段上げて確かめ直します（バースト的に重くなるプラグインは数秒では見逃すため）。
- 続けて IO サイクル使用率を 0.75、0.5、0.35、0.25 と下げ、同じように見て、最後に 12 秒の確認をします（負荷の最大が使用率の 60 % を超えたら不採用）。
- 全部で 1 分ほどかかり、その間は何度かデバイスを開き直すので音が途切れます。サンプルレートは変えません。結果はステータス行に出ます。

#### 余裕あり

バッファの探し方（下げる、上げる、12 秒の確認）は最速と同じです。違いは次の 3 点です（`LatencyTuner` の `TuneMode` で切り替え、最速の処理は変えていません）。

1. 3 秒の確認と 12 秒の確認のあいだ、背景に合成の負荷を掛けます（`src/BackgroundLoad.*`）。
   - 作業スレッドは通常の優先度（リアルタイムではない）で、数は物理コア数から 1 を引いた数です（最低 1、`juce::SystemStats` で数えます）。
   - 各スレッドが数 MB のバッファを回し続け、CPU とメモリの帯域を取り合います。
   - デバイスを開き直して落ち着くまで（サイクルごとの確認の前の settle）は止めておき、そのあと始めます。
   - 探索が終わったとき、中止したとき、デバイスが変わって打ち切ったとき、開き直せなかったとき、ウィンドウを閉じたときは、必ず止めて join します（デストラクタでも止めます）。
2. 安定とみなす条件が厳しく、負荷の最大がバッファ時間の 50 % 以下です（オーバーロードと遅れたコールバックが 0 であることは同じ）。
3. IO サイクル使用率は既定のままにして、使用率の段階を飛ばします。始める前に使用率が下げてあれば既定に戻し、中止や失敗のときは元の値に戻します。

進行中のステータス行には「（背景の負荷を掛けています）」と出ます。結果は「最小遅延（余裕あり）: バッファ N / サイクル使用率は既定のまま」のように、方式の名前を含みます。背景の負荷は実際のゲームの代わりにはなりません。目安として、余った CPU を取り合う状況を作るだけです。

</details>

<details>
<summary>IO サイクル使用率</summary>

IO サイクル使用率（`kAudioDevicePropertyIOCycleUsage`）は、機器セットについて「コールバックが 1 サイクルのうちどれだけを使うか」を表す 0 から 1 の値です。

- 小さくすると HAL が出力の時刻を早め、申告される遅延が `バッファ x (1 + 使用率) + safety` になります（既定の 1.0 で `バッファ x 2 + safety`）。
- コールバックが実際に起動する時刻は変わらず、その代わりコールバックに許される時間が `使用率 x バッファ` に減ります。
- 測定に使った Mac では、64 サンプルで 1.0 から 0.25 にすると 1.09 ms 下がりました。重いプラグインのチェーンではオーバーロードが出ます。

</details>

<details>
<summary>遅延の内訳の計算と、仮想デバイスの計測の仕組み</summary>

内訳の表（LATENCY BREAKDOWN）です。値はデバイスやチェーンが変わるたびに更新します（250 ms ごとに読み直します）。ウィンドウの高さが足りないときは、パネルの中がスクロールします。

| 行 | 中身 | 由来 |
| --- | --- | --- |
| 入力機器の申告値 | 入力側の latency + safety + stream | 申告（HAL） |
| 入力バッファ | バッファ 1 回分 | 申告 |
| プラグイン N | そのスロットの `getLatencySamples()`。バイパス中は 0（経路から外れているため） | 申告 |
| 出力バッファ + safety | バッファ x IO サイクル使用率 + 出力側の safety | 申告 |
| 出力デバイスの申告値 | 出力側の latency + stream | 申告 |
| 出力デバイスの実測超過分 | 出力デバイスが申告せずに足している分（下の節）。未計測なら「未計測」 | 実測 |

各行に samples と ms、バーを出し、いちばん大きい行に「ここが最大」の印と色の帯を付けます。申告の行は枠だけのタグ（申告）と塗りのバー、実測の行は塗りのタグ（実測）と斜線のバーで、色がなくても見分けられます。合計は、超過分が未計測のあいだは「超過分を除く」と書きます。4 つのテーマ（RACK '84 / TERMINAL / DESKTOP '95 / NEON）とも、パネルの枠はテーマのもの、文字と印の色はテーマの配色（文字色と選択色）を使います。

計算の流れ:

- 計算は `src/Breakdown.cpp` の `declareHost()`（HAL の数字を足す）と `computeBreakdown()`（行にする。画面に依存しない純粋な関数）の 1 か所だけです。数字は `Engine::getAggregateNumbers()` と `Engine::getCycleUsage()` から来ます。
- `--measure` の `declared`（HAL の時刻から出す値）と同じ区間で、IO サイクル使用率が既定の 1.0 のとき一致します（44.1 kHz、64 サンプルで 64 + 64 + 5 + 4 = 137 サンプル = 3.107 ms。`--selftest-timing` が確かめます）。
- `--measure` は、同じ関数が出した値を `HAL numbers declare ...` の行にも出します。
- 使用率を下げているときは、出力バッファを使用率倍で数えます（「IO サイクル使用率」の項）。
- 画面の大きな数字（LCD）と「合計」も同じ計算結果を使うので、パネルの合計と一致します。超過分を計測済みなら、どちらもそれを含みます。

#### 仮想デバイスの計測

「仮想デバイスを計測」は、`--measure`（`Measure.cpp`）と同じ計測をアプリの画面から行います。`measure::Session` が計測を段階的に進めます。`LatencyTuner` と同じく、画面のタイマーが 250 ms ごとに `tick()` を呼ぶ形で、メッセージスレッドを止めません。録音の相関計算だけ別スレッドで走らせます。`--measure` は同じ `Session` を、メッセージループを回しながら最後まで進める `runSession()` として使います。

- 押すと確認ダイアログが出ます。計測の間（数秒）、出力デバイスに試験音が流れ、マイクの音は止まり、通話中は相手に試験音が聞こえます。「計測する」のときだけ始めます。
- 計測中は、MIN LATENCY、デバイスの選択、プラグインの追加・削除・並べ替え・バイパスを無効にします。MIN LATENCY の実行中は計測ボタンが無効で、計測中は MIN LATENCY が無効なので、同時には走りません。ボタンは「中止」になります。
- 試験音の間、チェーンは経路から外れます（プラグインが試験音を変えないように）。終わり方が完了でも失敗でも中止でも、ウィンドウを閉じたときでも、`ScopedSetup` がデバイスの設定、IO サイクル使用率、チェーンの完全バイパス、試験音の注入を元に戻します。計測中にデバイスが変わったら中止します。
- 試験音を 6 回送り、信頼できた回が 3 回以上あれば、`excess` の中央値を結果にします。足りないときは採用せず、ステータス行にそう書きます。失敗の理由もステータス行に出ます。

結果は、出力デバイス名とサンプルレートと組で設定ファイルのルートに保存します。

    <LATENCY_EXCESS outputDevice="Loopback Audio" sampleRate="44100" excessMs="17.415" runs="6" measuredAt="2026-11-10T14:23:00.000+09:00"/>

- いつ測ったかは内訳の下に出ます。
- 次回起動時、同じ出力デバイスで同じレートなら表示します。
- デバイスかレートが変わると「未計測」に戻り、設定ファイルからも消えます（元に戻しても古い値は戻りません）。
- 起動時にデバイスが開けなかったときは、デバイスを判断できないので保存した値を残します。
- この要素がない古い設定ファイル、値が壊れた要素（NaN、負の数、0 回など）は、どちらも未計測として読みます。

#### プラグインごとの処理時間の測り方

内訳の下に、各スロットの `processBlock` の所要時間を、1 バッファの時間（64 サンプル、44.1 kHz なら 1.45 ms）に対する割合で出します。直近 3 秒の、全ブロックの平均と、いちばん長かった 1 ブロック（最大）です。最大がいちばん大きいスロットに「ここが重い」の印を付けます。バッファを下げられなくするのはいちばん遅い 1 ブロックなので、平均ではなく最大で選び、同じなら平均が大きい方を選びます。

- 測り方は、経路に入っているスロットの前後に、バッファに触らない 2 つの素通しの小さな処理（`Chain.cpp` の `TimingProbe`）を置き、間の時間を読みます。
- オーディオスレッドではロックも確保もログもなく、時計を読んで数個のアトミックを足すだけです（`ProcessTimer`、`ProcessTime.h`）。メッセージスレッドが 250 ms ごとに取り出します。
- `rewire()` の組み方（入力 → 経路に入るスロット → 出力）は変わりません。
- 入力のないプラグイン（ジェネレーター）、出力のないプラグイン、入力の信号がないときは、グラフが前後の小さな処理の順序を決められないので包まず、そのスロットは「--」（計測なし）になります。
- バイパスしたスロットと強制バイパス中は、プロセッサを止めるだけでなく小さな処理も外すので、完全バイパスのとおり遅延 0・CPU 0 のままです。小さな処理は遅延を足しません。
- `--selftest-processtime` の実測では、プラグイン 1 個あたり（小さな処理 2 つとグラフのノードを含めて）64 サンプルのバッファの 0.005 % ほどでした。
- バッファサイズやレートが変わると、割合の意味が変わるので、それまでの測定値は捨てます。

</details>

<details>
<summary>モニター出力の仕組み</summary>

モニター出力の項目と、設定時の挙動です。

| 項目 | 中身 |
| --- | --- |
| モニター出力（チェック） | オンにするまで、機器セットの作成もデバイスを開くことも一切しません（既定はオフ） |
| モニター機器 | 出力を持つデバイスの一覧。メイン出力と同じデバイスも選べます |
| ch | 左右の組。1/2、3/4、... のように奇数番号から始まる組を選びます（保存値は 0 始まりの最初のチャンネルで、3/4 は 2） |

通話の相手に届く音（メイン出力）は変わりません。モニターには、メイン出力に出る信号（プラグインを通した後、バイパス中はバイパスした信号）がそのまま複製されます。

#### 機器セットを作る理由

JUCE の CoreAudio デバイスは、入力 1 台と出力 1 台を 1 つの機器セットにまとめて開き、時計は出力デバイスのものを使います。出力は 1 台しか渡せないので、モニターを使うときは WIREVOX が HAL（`AudioHardwareCreateAggregateDevice`）で「メイン出力 + モニター機器」の機器セットを作り、それを JUCE に出力デバイスとして渡します（`src/Monitor.cpp`、HAL の部分は `src/Hal.cpp` の `PrivateAggregate`）。

- 時計は、メイン出力です（`kAudioAggregateDeviceClockDeviceKey` と main sub-device）。モニター機器にはドリフト補正（高品質）を付けます。ドリフトの処理は全部 HAL がします。
- コールバックでは、メイン出力のチャンネルだけをプラグインのチェーンに渡し、チェーンが書いた 1 チャンネル目と 2 チャンネル目（メインが 1 チャンネルなら 1 チャンネル目を左右に）を、モニターの組へ複製します（`copyToMonitor`）。確保もロックもありません。メインのチャンネルが 1 つも有効でなければ、モニターは無音です。
- モニター機器がメイン出力と同じデバイスなら、機器セットは作りません。同じデバイスの、もう 2 チャンネルとして扱います。その組をメイン出力のチャンネルに含めていると開けず（JUCE が保存するチャンネル選択を勝手に狭めないため）、モニターをオフに戻して理由を出します。チャンネル一覧には、その組が「[モニター]」と出ます。
- JUCE の `AudioDeviceManager` には機器セットを見せません。`MonitorDeviceType` が CoreAudio のデバイス型の前に立ち、モニターがオフのあいだは CoreAudio のデバイスをそのまま返します。オンのときは `MonitorDevice` を返し、これがデバイス名、チャンネル一覧、有効なチャンネル、遅延の申告をメイン出力のものとして見せます。
- デバイスのパネル、保存される DEVICESETUP、`LATENCY_EXCESS`（出力デバイス名とレートが鍵）、MIN LATENCY の「デバイスが変わっていないか」の確認、仮想デバイスの計測は、どれも JUCE が返すメイン出力の名前をそのまま使うので、機器セットの名前はどこにも現れません。
- JUCE は、渡された機器セットを自分では開かず、中の sub-device を並べ直して、もう一段自前の機器セットを作ります（`juce_CoreAudio_mac.cpp` の 1192 から 1200 行、1218 から 1264 行、`AggregateDeviceDescription`）。そのため WIREVOX の機器セットは、JUCE のデバイスが生きている間だけ必要で、デバイスを閉じるとき、モニターを切るとき、メイン出力を替えるとき、終了するときに壊します（`MonitorDevice` のデストラクタ。JUCE 側を先に片付けてから壊します）。

#### 機器セットは private にした

`kAudioAggregateDeviceIsPrivateKey` を 1 にして作ります（JUCE 自身の機器セットも同じで、ログ出力を有効にしたときだけ公開、`juce_CoreAudio_mac.cpp` の 1303 行）。private でも JUCE の `AudioDeviceManager` が名前で開けると判断した根拠は次のとおりです。

- `CoreAudioIODeviceType::scanForDevices()`（2321 から 2354 行）は `kAudioHardwarePropertyDevices` の一覧（966 から 969 行）を読み、`_JucePrivateAggregateDevice_` で始まる名前だけを除きます。ほかの名前の機器セットは隠しません。
- private な機器セットは、作ったプロセスからは見えます。このアプリの `findJuceAggregate()`（`Hal.cpp`）は、JUCE の private な機器セットを同じ一覧から見つけていて、`--measure` の実測はそれに頼っています。HAL のヘッダは、private な機器セットを「作ったプロセス専用で、起動をまたいで残らない」と説明しています。
- 公開にすると、Audio MIDI Setup と他のアプリに出て、異常終了の残骸が残ります。名前で消すのは危ないので UID の接頭辞で見分ける必要が出ますが、private ならプロセスが終われば HAL が消すので、その掃除は要りません。

名前と UID:

- 名前は `WIREVOX monitor <pid>.<連番>` です。HAL の一覧は破棄より少し遅れて更新されるので、次を作る前に前のが一覧から消えるのを最大 200 ms 待ち、同じ名前を二つ作らないようにします。
- UID は `local.nil.wirevox.monitor.<pid>.<UUID>` です。
- デバイスの一覧には出しません（名前の接頭辞で除きます）。
- この機器セットは作ったプロセス専用（private）で、プロセスが終われば HAL が消すので、残骸を掃除する処理は入れていません。
- 作った後に、JUCE が一覧に載せたか（名前を開けるか）を確かめます。載っていないまま名前で開くと、JUCE は出力のない入力専用デバイスを作ってしまうからです。

#### 保存と読み込み

設定ファイルのルートの子要素です。

    <MONITOR enabled="1" device="My Interface" firstChannel="2"/>

- 選んだことがなければ書きません。この要素がない古い設定ファイルは、モニターをオフとして読みます。
- 機器名が空、チャンネルが数字だけの文字列でない（負の数、小数、空、4 桁を超える数）、`enabled` が真でない場合も、オフです。
- 機器が見つからないときは選択を残して待機します。チャンネルがその機器の範囲を超える（最後のチャンネルから始まる組も含む）ときは、開くときにオフに戻して理由をステータス行に出します。
- どちらの場合も DEVICESETUP やチェーンには触れず、次の保存では `enabled="0"` のまま、機器名とチャンネルは残ります。

#### 失敗したとき

- 機器が「今ないだけ」の場合（起動時にメイン出力の Loopback がまだない、モニター機器の電源が切れている、実行中に抜けた）は、保存した選択（`enabled="1"`）を消しません。ステータス行に待機中と理由を出し、メイン出力だけで動かして、デバイス一覧の名前が実際に変わって機器が現れたときに 1 回だけ試し直します（同じ一覧では 2 回見ません）。
- 一覧にあっても HAL で解決できない機器（同名が複数、機器セットなど）は待機にせず、理由を出してオフにし、候補にも出しません。
- MIN LATENCY や計測の実行中に起きたことは、それが終わった時点と 250 ms のタイマーで拾います。
- チャンネルが機器の範囲を超える、組がメイン出力と重なる、機器セットを作れない・開けない、のように選択そのものが成り立たない場合と、ユーザー自身がオフにした場合だけ、保存を `enabled="0"` にします。
- デバイスを開いた後でエラーが返った場合（再オープン、起動、計測の後始末、JUCE 自身の再オープン）も、モニターをオフにして理由（エラー文つき）を 1 回出し、メイン出力だけで開き直します。
- 機器セットを作れない、JUCE が一覧に載せない、開けない、モニター機器やチャンネルがない、のどれでも、メイン出力だけでデバイスを開き、モニターはオフに戻して、理由をステータス行に出します（機器セットは残しません）。実行中にモニター機器が抜かれたときは、250 ms ごとの確認で見つけ、同じようにメイン出力だけで開き直します。

#### 遅延の内訳と計測への影響

- 内訳の行は、これまでどおりメイン出力の経路を表します。機器セットにモニター機器が入ると、HAL の出力側の数字（latency、safety、stream latency）は、モニター機器の値で大きくなり得ます。そこで `Engine::getAggregateNumbers()` は、モニターが動いているあいだ、出力側をメイン出力デバイス自身の値に置き換えます（入力側とバッファは機器セットのまま）。
- モニターの経路は、LCD に 1 行だけ足しました（「モニター経路（申告値。デバイス間のドリフト補正は含みません）」）。入力側とプラグインは内訳と同じで、出力側はモニター機器自身の値（バッファ x 使用率 + safety + latency + stream latency、`declareMonitorPath`）です。ドリフト補正が足す遅延は、誰も申告しないので入っていません。
- 「仮想デバイスを計測」（`measure::Session`）は、モニターがオンなら、計測のあいだだけモニターを外してデバイスを開き直し、終わったら（失敗や中止でも）`ScopedSetup` が戻します。機器セットに第 2 の出力が入ると、HAL の時刻と試験音の経路が変わり、メイン出力の超過分を測れなくなるためです。`--measure` などはモニターを使いません（設定のモニターを読まず、オフで開きます）。

#### `--probe-monitor`

実機で、機器セットが作れて、使えることを、音を出さずに確かめます。

```sh
APP=build/Wirevox_artefacts/Release/WIREVOX.app/Contents/MacOS/WIREVOX
"$APP" --probe-monitor "BlackHole 2ch" "My Interface"
```

- アプリと同じ関数で機器セットを作ります。
- 関係するデバイス（メイン出力とモニター機器）の公称レートを、作る前、作った後、壊した後に出します（変わっていれば `CHANGED`）。
- 機器セットのクロックの UID、sub-device ごとの出力チャンネルの範囲、機器セットのチャンネル番号から sub-device のチャンネルへの対応を出します。
- この処理の HAL の一覧と JUCE のデバイス走査に載るか、壊した後に一覧から消えたかも出して、壊します。
- IO は始めず、レートは書きません（HAL が自分で変えた場合は `CHANGED` で分かります）。
- 壊した後は、HAL の一覧が非同期に更新されるので、最大 1 秒まで一覧を見て消えるのを待ち、`AudioHardwareDestroyAggregateDevice` の OSStatus と、待った後のレートも出します。
- 終了コード: 0 が問題なし、2 がデバイスが見つからない、3 が作れない、4 がレートが動いた、5 が一覧に載らない（または壊しても残る）。

</details>

<details>
<summary>バイパスの仕組み</summary>

バイパスしたスロットは、信号の経路から完全に外れます（グラフの接続を外し、プラグインの処理も止めます）。

- 遅延は 0、CPU も 0 になり、画面に出る遅延にも反映されます。
- プラグインのインスタンスと状態は残ります。バイパスを戻すと、プラグインを `reset()` してから経路に戻します（古い音が残らないように）。
- 経路から外れるプラグインは、グラフを組み直して新しい処理順に切り替わったあとで止めます。先に止めると、グラフが止まったノードのバッファを消すため、切り替えの間は音が欠けます。
- `--selftest-chain` は、処理スレッドを回し続けながら 400 回切り替えます。止めてから組み直す順序では 7000 ブロック前後が無音になり、組み直してから止める順序では 0 から数ブロックでした。数ブロックは、新しい処理順に切り替わる直前に動き始めていたブロックです。
- 以前の「プラグイン内蔵のバイパス」は、バイパス中も遅延と処理が残っていました。

</details>

<details>
<summary>かんたん表示とテーマの実装</summary>

かんたん表示:

- 表示は設定ファイルのルートの `view` 属性（`simple` か `detail`）に保存し、次回起動時に復元します。
- かんたん表示（`simple`）に出る項目の詳細:
  - 合計の遅延（大きな数字。LCD と同じ値で、実測した超過分があれば含みます。未計測のあいだは「※ 超過分を除く」と添えます）。
  - いちばん大きい部分を 1 行（「いちばん大きいのは: 出力デバイス（17.4 ms）」）。
  - 状態を 1 行（「安定」か「音切れ N 回」と、負荷の最大）。音切れはオーバーロードと遅れたコールバックの合計で、リセット以降の数です。
  - 気をつけることがあるときだけ「注意:」の行（サンプルレートの食い違い、モニターの待機や失敗の理由、いちばん重いプラグインがバッファ時間の 70 % 以上）。
  - 遅延の内訳とプラグインごとの処理時間のパネルは畳み、「仮想デバイスを計測」のボタンだけを残します（枠の名前は MEASURE）。チェーンの一覧が空いた高さを使います。
  - デバイスのパネル、モニター出力、MIN LATENCY、プラグインの追加はそのままです。
- 詳細表示（`detail`）は、これまでどおりの画面です。
- 設定ファイルに `view` がない（この機能より前から使っている）場合は詳細表示で始まり、見た目は変わりません。設定ファイルがまだ無い初回起動はかんたん表示で始まります。未知の値は詳細表示です。
- 文言の決定は `src/Breakdown.cpp` の `summarise()`（画面に依存しない純粋な関数）にあり、`--selftest-breakdown` が確かめます。

テーマ:

- 選んだテーマは設定ファイルのルートの `theme` 属性に保存されます。未知の値は `rack84` になります。
- テーマは `src/Theme.h` の `Theme`（LookAndFeel 兼、パレット・フォント・寸法・描画）を実装した 1 ファイルで、`src/Themes.h` に生成関数を宣言し、`src/ThemeRegistry.cpp` の表に 1 行足すと増やせます（`CMakeLists.txt` のソース一覧にも 1 行）。

</details>

<details>
<summary>設定ファイルと旧名からの引き継ぎ</summary>

設定（デバイス、チェーン、各プラグインの状態、バイパス、仮想デバイスの実測結果、モニター出力の選択、表示と MIN LATENCY の方式）は `~/Library/Application Support/WIREVOX/settings.xml` に保存し、次回起動時に復元します。

- 新しいファイルがまだ無いときは、旧名の設定を新しい順に探し、最初に見つかったものの写しを起動時に一度だけ作って引き継ぎます。
- 探す場所は、旧名 VOXRACK の `~/Library/Application Support/VOXRACK/settings.xml`、その次に旧名 mic-fx-host の `~/Library/Application Support/mic-fx-host/settings.xml` です（旧フォルダには触りません）。
- `--settings <file>` を付けると、そのファイルを設定として使い、引き継ぎもしません（見た目の確認など、実際の設定に触れたくないとき用）。このときに限り二つ目の WIREVOX を起動できますが、`..` やシンボリックリンクを通っていても、指すファイルが実際の設定なら二つ目は起動できません。
- 読み込めないプラグインは赤字の行で残り、状態は失われません。
- 設定ファイルが壊れていて読めないときは、上書きする前に同じフォルダの `settings.unreadable.xml` へ写しを残します。
- プラグインの読み込み中にアプリごと落ちた場合、次の起動ではチェーンを読み込まず、元の設定を `settings.crashed.xml` に残します。

プロダクト名は `CMakeLists.txt` の `MFX_PRODUCT_NAME` ひとつで決まります（`.app` の名前、ウィンドウタイトル、設定フォルダ、バンドル ID `local.nil.wirevox`）。バンドル ID が変わったため、旧名（VOXRACK、mic-fx-host）から移ると、マイクの許可を macOS がもう一度確認します。マイクへのアクセスは初回に macOS が確認します。許可しないと入力は無音になります。

</details>

<details>
<summary>テスト（ctest と <code>--selftest-*</code>）</summary>

```sh
APP=build/Wirevox_artefacts/Release/WIREVOX.app/Contents/MacOS/WIREVOX

"$APP" --list-devices                          # 入出力デバイス名を表示して終了
"$APP" --selftest "/Library/Audio/Plug-Ins/VST3/TDR Nova.vst3"
"$APP" --selftest-settings                     # 旧フォルダ（VOXRACK、mic-fx-host）からの設定の引き継ぎを一時フォルダで確認
"$APP" --selftest-correlate                     # 遅延の推定が小数サンプルまで合うか
"$APP" --selftest-chain                         # バイパスしたスロットの遅延・CPU・状態、切り替え中に音が欠けないか
"$APP" --selftest-sweep                         # 総当たりの最速選び
"$APP" --selftest-timing                        # 遅延の計算を作り物の HAL 時刻で確かめる。試験音の注入でマイクが漏れないか
"$APP" --selftest-engine                        # 偽のデバイス層で、MIN LATENCY（最速と余裕あり）・保存される設定・設定の復元・途中で kill した場合
"$APP" --selftest-breakdown                     # 遅延の内訳の計算、最大の行、実測した超過分の保存と復元（デバイス・レートが変わると未計測に戻る）、かんたん表示の文言、表示と探し方の保存
"$APP" --selftest-processtime                   # プラグインごとの処理時間の集計、ここが重いの判定、素通しの小さな処理が経路を壊さないこと
"$APP" --selftest-monitor                       # モニター出力の設定の保存と復元、チャンネルの割り当て、モニターの組への複製、失敗時のメイン出力だけへの退避
(cd build && ctest)                            # 上の確認をまとめて実行（--selftest のプラグイン分は、プラグインが入っているときだけ）
```

ctest に載せるプラグインは `-DMFX_TEST_PLUGINS="パス1;パス2"` で変えられます。

各テストの内容:

- `--selftest`: ウィンドウもオーディオデバイスも使わず、GUI と同じ `Chain` とグラフでプラグインを読み込み、48 kHz・64 サンプルのブロックで 3 秒処理します。プラグイン名、報告された遅延、出力のピーク、無音でないか、バイパス時にモノ入力が左右に届くか、チェーンを XML にして復元したときに同じになるかを確認します。成功で終了コード 0、読み込み失敗などで 0 以外です。
- `--selftest-settings`: 一時フォルダの中だけで、旧設定（VOXRACK、mic-fx-host の順）が新しい場所へ写されること、両方あれば VOXRACK が優先されること、旧ファイルが残ること、新しいファイルが既にあれば上書きしないことを確認します。
- `--selftest-engine` と `--selftest-timing`: どちらもデバイスを開きません。
  - 前者は CoreAudio の代わりに偽のデバイス層（`src/FakeAudioDevice.h`）を差し込み、MIN LATENCY の完了・中止・失敗・デバイスの切り替え、その間に書かれる設定、`ScopedSetup` の復元、子プロセスを探索の途中で kill した場合を確かめます。
  - 後者は 48 kHz・64 サンプルのホストと録音側のバッファの作り物の時刻で、遅延の計算（サイクルの突き合わせ、録音側の下限の符号、1 バッファのずれ）を確かめます。
- `--selftest-engine` の余裕あり分: 背景の負荷を差し替えられる部品（`BackgroundLoad`）の偽物で、実際には CPU を使いません。同じ負荷の見え方（64 サンプルで 62.5 %）に対して、次を確かめます。
  - 最速は 64 のまま、余裕ありは 128 まで上げること。
  - 余裕ありが使用率を一度も設定せず、前の値を既定に戻すこと。
  - 負荷が落ち着いたあとに始まり、完了・中止・デバイスの切り替え・開き直し失敗・何も安定しない場合・デストラクタのどれでも止まること。
  - 最速では負荷を始めないこと。
  - 本物の負荷は、始める、止める、二重に止める、動いたまま壊すだけを確かめます。
- `--selftest-breakdown`: 偽のデバイス層で、行の足し算（137 サンプル = 3.107 ms、合計 20.522 ms）、バイパス中の 0、最大の行の判定、設定の保存と復元、デバイスかレートが違うと未計測になること、古い設定ファイルと壊れた値が読めること、計測が始められないときに何も変えないことを確かめます。かんたん表示の文言（最大の行の言い方、安定と音切れ、3 つの注意、超過分が未知のときの添え書き、デバイスなし）と、`view` と `tuneMode` の読み書きも同じ中にあります。
- `--selftest-processtime`: 別スレッドが書きながら読んでも取りこぼさないこと、確認する区間と割合の計算、最も重いスロットの選び方、実際のチェーンとグラフでの計測（バイパス、移動、削除、モノのプラグイン、遅延のあるプラグイン）、小さな処理のコストを確かめます。
- HAL が要る計測の本体（試験音と録音）は、実機でしか確かめられません。
- `--selftest-monitor`: 偽のデバイス層（HAL の代わりに `FakeMonitorBackend`）で、モニター出力の次を確かめます。
  - 設定の保存と復元（要素がない古いファイル、壊れた値はオフ）。
  - チャンネルの割り当て（メインが 0・1・2 チャンネル、モニター機器のチャンネルが先に並ぶ機器セット、同じデバイス、組が収まらない場合）。
  - コールバックでの複製（空のチェーン、プラグイン、スロットのバイパス、計測の強制バイパスのどれでも、モニターはメイン出力と同じ）。
  - オフのあいだは何も作らず JUCE のデバイスを包まないこと。
  - オンのとき、デバイス名・チャンネル一覧・保存される DEVICESETUP・`LATENCY_EXCESS`・MIN LATENCY がメイン出力の名前のままで、機器セットの名前が設定ファイルのどこにもないこと。
  - オンとオフと切り替えと終了で、機器セットが残らないこと。
  - 失敗（機器がない、チャンネルが範囲外、1 チャンネルの機器、作成の拒否、一覧に載らない）でメイン出力だけに戻ること。
  - 実行中に機器が抜けた場合、計測がモニターを外して戻すこと。
  - 実際の HAL での機器セットの作成、JUCE がそれを開くこと、チャンネルの対応、レートが変わらないこと、モニターの音は、実機でしか確かめられません（`--probe-monitor` が最初の 3 つを音なしで確かめます）。

</details>

<details>
<summary>設計上の判断（実測に基づく調整の結果、下限、範囲外）</summary>

#### 実測に基づく調整の結果

| 調整 | 結果 |
| --- | --- |
| オーバーロードと負荷の計測 | 採用。JUCE 9.0.5 は `getXRunCount()` を持つが `running` を true にしないため常に -1 を返す（`juce_CoreAudio_mac.cpp` の 1377、1391 行）。自前の HAL リスナーとコールバック時間の計測に置き換えた |
| バッファサイズの下限 | 不可。HAL は 15 などの値も受け付けるが、JUCE が申告と違うコールバックサイズを検出して（1587 行）デバイスを再起動し、リストの値に丸めた設定へ戻す（`requestBufferSize` の 1833 から 1836 行、`AudioDeviceManager` の 928 行）。2 のべき乗以外は選べない |
| IO サイクル使用率 | 採用（MIN LATENCY の第 2 段）。実機で最大 1.1 ms 低下、負荷が軽いときだけ |
| バイパスで経路から外す | 採用。TDR Nova は 48 kHz で 184 サンプルの遅延が 0 になる |
| 計算の経路の見直し | 余分なバッファ遅延は無し。入力は JUCE の 1 回のコピーと、グラフの入出力 2 回のコピーだけ（`juce_AudioProcessorPlayer.cpp` 61 から 104 行、`juce_AudioProcessorGraph.cpp` の 995 行の `AudioInOp` と 1009 行の `AudioOutOp`）。直列のチェーンではグラフの遅延補償は働かない |
| デノーマル対策（FTZ） | 不採用。負荷の平均も最大も差が出なかった |
| オーディオワークグループ | 不可。`AudioProcessorGraph` は `audioWorkgroupContextChanged` を子のプラグインに渡さず、VST3 にはその API がない |

#### 下限と、これ以上下げるには

この構成（アプリが機器セットの 1 本の IOProc で入出力を同時に処理する）で、ホスト側の下限は

    入力デバイスの latency + safety + バッファ 1 回 + 出力の safety + latency   （IO サイクル使用率 → 0）
    = 0 + 5 + 64 + 4 + 0 = 73 サンプル = 1.66 ms（44.1 kHz、64 サンプルのとき）

です（使用率 1.0 では 137 サンプル = 3.107 ms）。

- 入力と出力でレートが違うと、これにドリフト補正（高品質のレート変換）が足す分が加わりますが、今回の方法では測れませんでした。
- さらにバッファを小さくすると下限は下がりますが、プラグインの最大処理時間に当たります。たとえば、32 サンプル（0.73 ms）のバッファに対して約 2 ms かかる瞬間があるプラグインもありました。
- これを超えて下げるには、Loopback を通さずアプリ自身が時計を持つ仮想マイクのドライバ（システムへのインストールが必要）にして、機器セットと Loopback の 768 サンプルを取り除く必要があります。このリポジトリでは作りません。

#### 範囲外

メニューバー常駐、プラグインの一括スキャン、プリセット UI、公証（Apple によるアプリの審査と署名）、AU ホスティングは入れていません（VST3 のみ）。

</details>
